Accounting Subledger Layers Mapped to IMS

Mapping of the L1-L4 tables from page 3 of accounting-subledger-design (1).pdf to objects found in tables.sql, view_udf.sql, and sp.sql.

Executive summary

IMS does not implement four cleanly separated layers. The core tblFin_Journal and tblFin_JournalPostings tables combine the conceptual L1 transaction and L3 journal. L2 accounting rules are mainly implemented in stored procedures rather than generic event/rule tables.
domain movement tables | TransactNum / ResPayId / InvoiceNum v tblFin_Journal (transaction and journal header) | TransactNum v tblFin_JournalPostings (signed double-entry lines and applications) | +-- balances calculated by UDFs +-- Fortegra Oracle interface tables

IMS-specific caveats

  1. L1 and L3 are collapsed. Cash receipt and claim-payment workflows create domain records and journal records together.
  2. L2 is code, not data. Accounting decisions and debit/credit construction are primarily embedded in stored procedures.
  3. Balance checking is procedural. CheckDistributionBalance(TransactNum) checks that signed lines sum to zero, but the supplied DDL does not show a database constraint guaranteeing this for every write path.
  4. Current GL balances are calculated, not stored. This differs from the proposed target acct_balance.
  5. Immutability is not guaranteed by the DDL. IMS supports void/reversal links, but the underlying tables remain updateable.
  6. Inbound staging is fragmented. The target acct_staging_transaction should be a new canonical table, not a rename of one legacy import table.

Recommended migration interpretation

New layerIMS extraction/source of truth
L1 transactions and movementsBuild canonical movements from tblFin_RemitterJournal, tblClaims_ReservePayments, tblFin_CheckRegister, tblFin_BankDeposit/detail, and application links. Retain IMS IDs as source-record IDs.
L2 events and rulesDerive event types from stored procedures and source-document codes, then express the procedures' posting decisions as versioned rules and rule lines. Do not treat journal templates as a complete rule engine.
L3 journalsMigrate tblFin_Journal and tblFin_JournalPostings together, preserving transaction number, signed amount, GL account, source links, currencies, and reversal relationships. Validate that every migrated transaction sums to zero.
L4 interfacesConsolidate source-specific imports behind acct_staging_transaction; generate Oracle GL from Fortegra_OracleJournalTransferData semantics and payment requests from Fortegra_OracleDataTransfer; ingest acknowledgements from the Oracle return tables.

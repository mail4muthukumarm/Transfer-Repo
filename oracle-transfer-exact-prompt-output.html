I found two separate Oracle outbound flows: payment/check transfer and general-ledger journal transfer. Only the payment flow has evidence of an inbound check-number reconciliation.

1. Outgoing payment/check flow

The main procedure is Fortegra_OraclePaymentTransfer.

Source records

It combines:

  • tblFin_CheckRegister — payee, address, payment method and check number
  • tblFin_Journal — transaction and posting date
  • tblFin_JournalPostings — payment amount, claim and reserve-payment IDs
  • tblFin_GLAccounts / tblFin_GLAccountTypes — cash-account identification
  • tblFin_BankAccounts — bank account used to build the pay group
  • tblClaims_Claim and tblQuotes — claim, policy and insured information
  • tblClaims_ReservePayments — check-stub comments
  • Entity views — fallback payee name and address

Only check payments are selected:

cr.PayMethodId = 'C'

The procedure selects payments whose posting date is on or after @Date and calculates the payment amount as the negative sum of cash-account postings. See the selection and enrichment logic.

Outbound staging table

Before creating a batch, it truncates:

TRUNCATE TABLE dbo.Fortegra_OracleDataTransfer;

It then populates Fortegra_OracleDataTransfer, whose columns represent Oracle’s payment interface:

  • Payee and address
  • Payment amount
  • Claim and policy numbers
  • Insured name and comments
  • Oracle ledger and pay-group values
  • GL accounting segments
  • IMS transaction number

The table definition is in tables.sql.

An external integration is presumably responsible for extracting this table and transmitting it to Oracle. That extraction code is not present in these SQL files.

2. Transfer logging

Every normal payment-transfer execution creates a batch header in:

  • Fortegra_OraclePaymentTransferLog

It stores the host and execution date.

Rows selected into the outgoing staging table are recorded in:

  • Fortegra_OraclePaymentTransferLog_Details

The detail includes:

  • Transfer batch ID
  • IMS transaction number
  • Reserve-payment ID
  • Amount
  • Transfer date

Definitions are in tables.sql, and population occurs after staging.

This log proves that a row was selected for a transfer batch. It does not prove Oracle received or successfully processed it.

3. Incoming check result

After Oracle processes or prints a check, a transaction-to-check-number mapping is expected in:

Fortegra_OracleCheckReconciliation

Its structure is:

ColumnPurpose
TransactNumIMS transaction identifier and primary key
CheckNumberOracle-assigned check number
DateAddedResponse arrival date
ProcessedIntended processing status
ProcessedDateIntended completion date

See the table definition.

At the beginning of the next payment-transfer run, IMS updates its check register:

UPDATE cr
SET cr.CheckNum = ocr.CheckNumber
FROM dbo.tblFin_CheckRegister cr
JOIN dbo.Fortegra_OracleCheckReconciliation ocr
  ON cr.TransactNum = ocr.TransactNum;

This is the incoming reconciliation step in sp.sql.

The practical lifecycle is therefore:

  1. IMS creates a payment transaction.
  2. IMS stages payment information for Oracle.
  3. External integration sends the payment.
  4. Oracle creates/processes the check.
  5. An external process loads TransactNum + CheckNumber.
  6. The next procedure run updates tblFin_CheckRegister.CheckNum.

4. Important gap in incoming processing

The provided SQL contains no procedure that inserts into Fortegra_OracleCheckReconciliation.

It also never:

WHERE Processed = 0

and never updates:

Processed = 1,
ProcessedDate = GETDATE()

Therefore, based on these SQL files:

  • The inbound file/API loader is outside this database script.
  • Every reconciliation row is reapplied on every normal transfer run.
  • Processed and ProcessedDate are currently unused by the shown procedures.
  • Triggers on the entire check-register table are disabled during the update.

5. Alternative payment procedures

Ad hoc transfer

Fortegra_OraclePaymentTransfer_Adhoc is a recovery/manual procedure.

It differs by joining an imported spreadsheet table:

dbo.[2025_NonIssuedPayments_20250715]

It should not be treated as the regular interface because the table name must be manually changed for each recovery batch.

On-demand transfer

Fortegra_OraclePaymentTransfer_OnDemand:

  • Returns payment rows directly
  • Uses an exact posting date
  • Does not truncate/populate Fortegra_OracleDataTransfer
  • Does not apply incoming check reconciliation
  • Does not write transfer logs

This appears to be a query/reporting or manual-extraction endpoint.

6. Separate outgoing journal flow

Fortegra_OracleJournalTransfer creates Oracle GL journal rows from:

  • tblFin_Journal
  • tblFin_JournalPostings
  • tblFin_GLAccounts
  • Claims, invoices, policies and company configuration

It:

  1. Separates positive postings as debits and negative postings as credits.
  2. Maps IMS data into Oracle ledger segments.
  3. Excludes a transaction if its TransactNum already exists as REFERENCE1.
  4. Writes the results into Fortegra_OracleJournalTransferData.

The target has PROCESSED defaulting to 0 and RECORD_CREATED defaulting to the current date. See its definition.

Suspicious journal implementation

The procedure builds:

Fortegra_TempOracleData_Debits
Fortegra_TempOracleData_Credits

But the final inserts read from:

Fortegra_OracleData_Debits
Fortegra_OracleData_Credits

instead of the newly built temporary tables. See the debit source and credit source.

Unless another process populates the permanent debit/credit tables, the freshly calculated journal data is discarded when the temporary tables are dropped. This looks like a defect or an incomplete legacy migration.

The SQL also contains no code that sends journal rows to Oracle or marks PROCESSED = 1; that responsibility must belong to an external integration process.
